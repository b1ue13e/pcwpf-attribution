## 🚨 P0 致命缺陷清单（不修必死）

### P0-1【数据完整性】同一模型同一切片的指标在正文与补充材料之间严重不一致

这是本报告最严重的发现。以下为原样转录的对比：

| 指标 | 正文 Table 2 Panel A | 补充材料 Table 5（Gaussian sweep, σ=0 行） | 附录 G scale_error_audit | 补充材料 ablation 表 |
| :--- | :--- | :--- | :--- | :--- |
| Ultra-LSNT clean R² | **0.9346** | **0.8728** | —（RMSE 9462.65） | 0.8727 |
| Ultra-LSNT clean RMSE | 8419.91 | — | **9462.65** | 9081.40 |
| DLinear clean R² | **0.9494** | **0.9379** | —（RMSE 6065.98） | — |
| LightGBM clean R² | **0.9563** | **0.9069** | — | — |
| iTransformer clean RMSE | 8004.05 | — | **7743.06** | — |

只有 Persistence 行（0.9175）两处一致，说明不是协议文字描述差异，而是**深度模型各行来自不同的运行批次/检查点，且论文从未说明哪一行是哪一版**。0.9346 vs 0.8728 这种 6 个点的 R² 差异不可能用"随机种子"解释。

佐证：结果目录里存在 `analyze_r2_issue.py`、`unified_results_final_fixed.csv`、`latency_fixed.csv`、`tau_sweep_fixed.csv` 等文件，说明历史上出过 R² 计算 bug 并打过补丁——如果仓库公开后审稿人顺着 commit 历史挖到这里，而论文里两套数字并存，会直接升级为 integrity concern。

**必须做**：选定唯一 canonical 证据链（manifest 锁定 run id），全文所有表格从同一份证据文件重新生成；在补充材料加"数字溯源表"（每个表格 → 来源 CSV → run manifest）。任何无法溯源到同一 manifest 的数字不得进入正文。

### P0-2【内部矛盾】正文算术不自洽：越限点数与百分比换算不上

正文 §5.1 原话："Across the 434,664 predicted points… 506 clean and 285 severe rated-power exceedances for the raw model versus 0 and 10 under FG-MoE"，同时给出百分比 0.1164% / 0.0741% / 0.0000% / 0.0076%。

核算：
- 434,664 × 0.1164% = 505.9 ≈ 506 ✓
- 434,664 × 0.0741% = **322.1 ≠ 285** ✗（285 对应 0.0656%，恰是补充材料 clip-control 协议的值）
- 434,664 × 0.0076% = **33.0 ≠ 10** ✗（10 对应 0.0023%，也恰是补充材料另一协议的值）

即正文把**两套不同协议（P1 physics_closure 与 clip-control）的点数和百分比混排在一句话里**。审稿人按一次计算器就会发现。

### P0-3【内部矛盾】Jump Gate skip rate：正文 vs 补充材料直接打架

- 正文 §4.2："τ=0.5 targets a skip regime of 0.12 and yields an average skip rate of **0.1155**"
- 补充材料 Table 15（tau_sweep）：τ=0.5 / 0.7 / 0.9 的 skip rate 全部为 **0.00%**，只有 τ=0.3 有 33.38%

两者不可能同时成立。要么正文引用的是另一批 12-seed 搜索运行而 τ sweep 表是单次运行，要么其中一份是旧结果残留。无论哪种，"Jump Gate 省算力"这条贡献的证据链目前是断的——而且 τ=0.5 时 skip=0 意味着 **Jump Gate 在主配置下根本没跳过任何东西**，那它对 latency 的贡献就是零，相关叙事需要重写。

### P0-4【内部矛盾】运维收益量级自相矛盾：−1.4% vs −11%~−24%

- 正文 §5.3 headline：total RT cost 30.88 → 30.44 M CNY，即 **−1.4%**
- 附录 Table（reserve_ratio_sensitivity）：同一界面下 Ultra FG ΔCost **−11.26% ~ −24.04%**

两处都声称是"matched raw stream 的 120 天铜板界面"。1.4% 和 18.5% 差了一个数量级，论文没有任何一处解释分母/界面差异。审稿人会直接问：到底省多少？如果真实答案是 1.4%，那么"operational value"这条卖点基本不成立；如果是 18.5%，正文 headline 写错了。

### P0-5【实验设计】缺失最关键的工业 baseline：「先清洗/插补，再上强模型」

论文的核心动机是"文献都在清洗后的数据上比模型，而我们直接在脏 SCADA 上预测"。那么最自然、也是每个工业审稿人必问的对照组是：**标准 QC/插补管线 + iTransformer/DLinear**。

而补充材料 Table 9（missingness + ffill/linear）实际上已经包含了这条线索的半成品，且结果对论文不利：**ffill 插补后 DLinear R²=0.9326，Ultra-LSNT 只有 0.8718**。也就是说"插补 + 简单模型"在该设定下反超论文主角 6 个点。这张表埋在补充材料里、只字未提它对主叙事的冲击——一旦审稿人翻到，论文的 motivation 会被反向利用。

**必须做**：把「插补+强 baseline」正式升级为正文对照层，正面回答"为什么不先修数据"。能赢就写进主表；赢不了就必须改写 motivation（例如论证在线场景不允许等待完整窗口、或插补引入的延迟/平滑偏差在调度层有害，并用调度实验证明）。

### P0-6【证据强度】关键不利诊断指标被埋在补充材料，与主叙事冲突

- 爬坡能力：Ultra-LSNT Ramp F1 = **0.3544**，DLinear = **0.5939**（补充 Table 11）。对备用/调度场景，爬坡段恰恰是最重要的部分，主角在最关键事件上明显更差。
- 尾部误差：Ultra-LSNT P95|e| = **11,940 kW**，DLinear = **2,484 kW**，差近 5 倍。
- 概率校准（补充 Table 12）：DLinear 的 NLL/CRPS/PICP 全面碾压 Ultra-LSNT（CRPS 670 vs 3353）。

"controller-side usable" 的叙事建立在平均 R² 和越限率上，但调度真正在乎的是爬坡和尾部。这些数字必须进入正文并给出解释，否则属于选择性呈现。

## 👤 Reviewer #1（理论/创新性）：Soundness 2/4 | Novelty 2/4 | Overall 4/10 | Confidence 4/5

**主要攻击点**：

1. **方法新颖性有限**：FG-MoE 本质是"软约束惩罚项 + 手工代理变量"。用分段功率曲线做输出惩罚是 PINN/约束学习里的标准 penalty method；真正算新的只有 $v^{proxy}$ 这个 horizon-aware 代理，而它有 **11 个站点标定系数**（η_h, Δ_max, s_v, α_s, β_s, ω_p^min, ω_r^min/max, ξ_r, s_κ），本质是一个手工调的 persistence 变体。审稿人会写："The contribution is an engineered heuristic, not a mechanism."
2. **循环论证风险**：guardrail 的包络由代理风速驱动，而代理风速本身是另一个（更差的）预测器。真爬坡时代理低估→包络压顶→合法高出力被惩罚，即 guardrail 系统性引入**低偏 bias**。论文报告了 positive-error exposure 下降，却从未对称报告 negative-error / 备用短缺的恶化。需要 bias 分解实验。
3. **代理误差的理论刻画缺失**：惩罚项的效果完全取决于 ‖v^proxy − v_true‖ 的分布，论文没有任何关于代理误差如何传播到惩罚梯度的分析，连一个经验散点（proxy error vs violation rate）都没有。
4. **跨站点失败坦白但削弱贡献**：Wind (US) zero-shot cut-region nonzero 57.6–100%，说明方法对采样率/站点标定极度敏感。"需要站点级重标定 11 个系数"在工业上等价于"每个场站都要做一次小课题"，泛化主张应进一步收缩。

**防御角度**：贡献重新定位为"评估协议 + 部署证据链"而非新算法；把 FG-MoE 写成 engineering mechanism design，配代理误差的敏感度理论 sketch。

## 👤 Reviewer #2（实验/基线）：Soundness 2/4 | Rigor 2/4 | Overall 4/10 | Confidence 5/5

1. **基线时效性不足（2026 年标准）**：主对照是 DLinear/iTransformer/TimeMixer/PatchTST（2022–2024）；Chronos-Bolt-Small 与 Moirai-2.0 只跑 zero-shot 小模型。缺：2024–2026 鲁棒预测/异常耐受文献的正面 baseline、fine-tuned TSFM、以及工业界实际用的 power-curve QC 管线（见 P0-5）。
2. **统计严谨性不达顶刊线**：headline FG-MoE 对比走 seed-42 单链；drift 增广只有 2 seed；missingness 3 seed；正文 Table 2 全表无误差棒。顶刊惯例是 ≥5 seed + std。DM 检验用 H=24 的重叠预测窗口，loss differential 强自相关，未做 HAC/Newey-West 长方差修正，p 值系统性偏小；且只"保留"3 个对照（retained contrasts），没有 vs DLinear/LightGBM 的 DM——而 DLinear 在 clean 上赢了主角，这看起来像是选择性报告。
3. **消融不完整**：kernel size 只扫了 {3,7,15} 三个点；λ₂ 只有 {0.01, 1.00} 两档有效点且 λ₂=1.0 时 R² 崩到 0.38——说明方法对 λ₂ 极敏感，却没有任何中间档（0.05/0.1/0.3）的细扫；"每个模块的贡献"（分解前端 / Top-K 路由 / Jump Gate / FG 惩罚）没有四因子正交消融表。
4. **算力与公平性**：LightGBM"固定超参不调"，而深度模型经过搜索——不对等比较；Ultra-LSNT-Full FP32 16.7 MiB vs Lite INT8 0.00 MiB（0.00 明显是测量/记账 bug，峰值内存不可能是 0）。
5. **部署时延数据多版本并存**：Ultra-Full 的 CPU 时延在正文 Table 4 是 6.69 ms（P95），补充 Table 13 是 3.714 ms，附录 P2 扫参表是 10.2–19.8 ms，ARM 表是 8.795 ms——四组数字没有统一的测量协议说明。

## 👤 Reviewer #3（落地/动机）：Soundness 3/4 | Significance 2/4 | Overall 4/10 | Confidence 4/5

1. **15 分钟 cadence vs 105 ms 时延 = 约束不紧**。三个数量级的余量意味着任何小模型都满足时延，"batch-1 控制器预算"作为 motivation 被人造化。更致命的是：iTransformer 在 ARM 上 1.38 ms vs Ultra-LSNT 8.80 ms——**更快且全面更准**，"为什么用 Ultra-LSNT 当载体"没有非循环的答案。目前论文的回答（"audited sparse carrier"）等于"因为我们审计了它"。
2. **调度层太玩具**：单火电机组、恒定 50 MW 负荷、铜板、固定比例备用规则。能源顶刊的电力审稿人会要求至少：时变负荷曲线、多机组、或直接用 RTS-24 层做主证据（目前 RTS-24 反而被降级到补充）。raw 预测 100% fallback、映射后才能闭合，说明结论强依赖人为 affine 映射——sensitivity 做了（好），但"结论是映射协议的函数"这一点需要更大字体写进摘要级声明。
3. **单站点 + 测试集季节覆盖不足**：测试期 2022-03-12 ~ 2022-06-30，只有春/初夏，没有冬季供热期与高风速季的极端工况；训练也仅 ~11 个月。超短期功率预测的季节漂移是常识性审稿问题。
4. **效果量偏小**：guardrail 修正的越限点占 0.1164%；headline 成本节省 1.4%（且与附录 −18.5% 矛盾，见 P0-4）。需要算一笔经济账：1.4% 的 RT 成本在一个 50 MW 风场对应多少万元/年，值不值得部署一套需要站点标定的系统。

## 🧪 最小化补实验清单（按投入产出排序）

1. **【0 成本，最高优先】数字统一工程**：单一 manifest → 全表格重生成 + 溯源表。解决 P0-1/2/3/4。
2. **【低成本】插补+强 baseline 对照**（P0-5）：ffill/linear + iTransformer/DLinear 在全部 corruption 档位下跑齐，进正文。
3. **【低成本】5-seed 补齐**：主表所有关键行补到 5 seed ± std；DM 检验加 HAC 修正，补全对照组合（含 vs DLinear）。
4. **【中成本】λ₂ 细扫 + 四因子消融**：λ₂ ∈ {0.01, 0.03, 0.1, 0.3, 1.0}；{分解, 路由, JumpGate, FG} 正交开关表。
5. **【中成本】代理误差分析**：v^proxy 误差分布、其对 violation/bias 的影响散点 + 一段理论 sketch，回答循环论证质疑。
6. **【中成本】爬坡/尾部指标进正文**：Ramp F1、P95|e|、CRPS 与调度缺额成本联动分析，把不利数字转化为"guardrail 恰好改善尾部"或诚实承认。
7. **【高成本但决定上限】调度层升级**：时变负荷 + ≥3 机组，或把 RTS-24 DC-OPF 升为正文本体并加 AC 可行性抽检。
8. **【高成本】第二站点正面验证**：再找一个 15 分钟级站点做"标定迁移"（而非 zero-shot）正面案例，把 Wind (US) 从"失败边界"变成"标定流程演示"。

## 🛡️ Rebuttal / 修改策略要点

- **对创新性质疑**：放弃"新算法"站位，改打"deployment-consistent evaluation protocol + causality-safe guardrail"——把审稿人引向证据链完整性。
- **对载体质疑**：要么给出 Ultra-LSNT 在稀疏路由下的独特价值证据（如 corruption-localized 场景的逐段优势），要么把 iTransformer 提为并列主载体，Ultra-LSNT 降为部署 profiling 对象（论文已半这么做，建议做彻底）。
- **对数字质疑**：不要逐条辩解，直接附上 manifest 溯源表 + 重跑脚本，一次性解决。
- **对调度质疑**：强调"fixed interface 是特性不是缺陷"，但必须先用时变负荷+多机组堵住"toy"的嘴。
