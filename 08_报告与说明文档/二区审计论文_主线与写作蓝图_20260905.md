# 二区审计论文：主线与写作蓝图（2026-09-05）

> 本文档是后续正文写作的权威蓝图。`主线定稿_20260904.md` 保留为证据状态快照，但不再直接充当论文结构。所有段落、图表和摘要主张均应服从本蓝图的 claim boundary。

## 一、现有主线是否已经整理好

### 结论

**概念主线已经形成，论文主线尚未完成。** 当前材料已有四个可连接的部件：生命周期框架、46篇 pilot field audit、PCT 静态代码案例、Wind-CN 下游压力测试；但现有 `manuscript_audit_final.tex` 仍是约 5 页的扩展摘要式草稿，而不是可投稿全文。

当前最主要的结构问题不是“结果不够多”，而是四个部件尚未形成严格的因果和论证层级：

1. taxonomy 是论文的**概念贡献**，不应在定义时混入 87.0%、47.8% 等结果；
2. field audit 是**描述性证据**，只能说明纳入语料中的报告与消融实践，不能证明发表偏倚或整个领域的真实比例；
3. PCT 是**单一可核验案例**，只能证明 paper–code divergence 的存在，不能证明这种偏差普遍存在，也不能声称它造成某个 RMSE 幅度；
4. stress test 是**D2/D5 为什么重要的探索性示例**，不是 Ultra-LSNT 的第二篇方法论文，也不是对 PCT 下游后果的直接复现。

因此，论文应从“四组结果并列展示”改成“一条审计逻辑逐层收紧”。

## 二、唯一中心命题

### 推荐的一句话主线

> **物理约束模型的可信度不取决于论文是否加入了一个 physics term，而取决于该约束能否沿其完整生命周期被追踪：它从何而来、在哪里施加、推理时依赖什么、代码是否忠实实现，以及研究是否真正隔离并报告其失败与代价。**

### 证据链

```text
概念缺口
“physics-constrained”把不同来源、阶段和依赖的约束压成一个标签
        ↓
框架
用 D1–D5 生命周期 schema 使约束可追踪、可编码、可核查
        ↓
pilot field audit
检查纳入语料是否报告这些信息、是否真正隔离约束、是否披露负面结果
        ↓
单一强案例
PCT 证明 paper specification 与 released implementation 可能在数学方向上分离
        ↓
下游压力测试
说明 clean accuracy 不能替代 corruption / safety / application-stage 检查
        ↓
实践产出
形成一个可复用的 constraint lifecycle audit protocol 与 reporting checklist
```

### 论文不能讲的故事

- 物理约束通常有害；
- 物理约束论文存在已被证实的发表偏倚；
- 46篇代表整个风电预测领域的无偏总体；
- PCT 的 reverse-JS 必然造成某个数量级的性能下降；
- Ultra-LSNT 或 FG-MoE 是全面最优的新方法；
- 下游压力测试已经验证五维 taxonomy 的因果正确性。

## 三、论文身份与标题

### 推荐文体

**scoping empirical audit + static software case study + exploratory downstream stress test**。

它既不是传统模型方法论文，也不是只做文献汇总的 narrative review。核心产出是“一个能被别人重复执行的审计对象、协议和证据链”。

### 推荐标题

首选：

> **Auditing Physics Constraints in Wind Power Forecasting: A Lifecycle Framework, Field Evidence, and a Code-Level Case Study**

备选：

> **From Physics Prior to Operational Claim: A Lifecycle Audit of Physics-Constrained Wind Power Forecasting**

暂不推荐：

> From Specification to Deployment: A Systematic Audit ...

原因是 `systematic` 会使审稿人立即按完整 PRISMA、双筛选者、检索可复现性和全量 inter-rater reliability 审查；`deployment` 又比现有 mapped dispatch 和单站 stress test 的外部效度更强。在第二真人完成46篇盲编、PRISMA-S信息闭合前，标题使用 `lifecycle audit` 或 `scoping field audit` 更稳。

## 四、四个研究问题

### RQ1：审计对象如何定义

**How can a physical constraint be represented as a traceable lifecycle object rather than a single undifferentiated “physics-informed” label?**

回答：D1 provenance、D2 application stage、D3 inference requirement、D4 implementation fidelity、D5 harm/ablation reporting。

### RQ2：纳入语料如何报告与验证约束

**Within the included pilot corpus, how are these lifecycle dimensions reported, and to what extent do ablations isolate the physical constraint itself?**

回答范围：46篇纳入语料中的分布；24/46 具有 strict physical isolation，22/46 仅为 module ablation；在已记录检索协议下，45/46 未找到公开代码，1/46 找到代码但存在 specification mismatch；未观察到显式 negative-effect/harm-metric 报告。

措辞必须使用 `within the included corpus`、`under the recorded search protocol`、`we did not identify`，不用 `the field universally`、`no code exists`、`publication bias is proven`。

### RQ3：paper specification 与公开实现是否一致

**For the only identified public codebase, does the implemented physical loss match the mathematical specification in the paper?**

回答：PCT 的联合 KDE 是正确的 paired 2D product-kernel KDE；唯一保留差异是论文标准 JS 与代码 reverse-JS-type 方向不同。只报告静态数学事实，不报告未经忠实复现的性能后果。

### RQ4：为什么生命周期审计对下游评价有实际意义

**What do controlled downstream stress tests reveal that clean-data accuracy alone does not?**

回答：clean 排名、严重传感器扰动下的鲁棒性、安全违规和 mapped dispatch value 并不一致；post-hoc clipping 可消除特定违规但可能付出较大精度代价。此部分仅作 exploratory illustration，不能外推为方法族定律。

## 五、四项贡献的最终写法

### C1：框架贡献

提出一个五维 Constraint Lifecycle Framework，把参数来源、施加阶段、推理依赖、实现忠实度和伤害/消融报告分开。真正的新意不是“多列了一张分类表”，而是明确指出：**训练期可合法获得的 historical-static prior 不等于推理期不可获得的 signal；constraint provenance 与 inference requirement 必须正交编码。**

### C2：pilot field evidence

在明确纳入标准下，对46篇全文进行 scoping audit，展示约束生命周期信息的分布、代码检索状态和消融语义。核心不是报很多比例，而是指出一个可验证的评价缺口：**作者所谓 ablation 不总是对物理约束本身的隔离。**

### C3：code-level case study

对唯一识别到的公开 PCT 代码库进行 specification-to-code 核查，确认 KDE 联合密度实现与论文数学等价，同时识别出 divergence 方向不一致。该案例同时展示审计的两种价值：发现真实 mismatch，也撤回经数学复核不成立的指控。

### C4：operational relevance

用一个明确标为 exploratory 的 Wind-CN stress-test 展示：仅有 clean accuracy 不能回答约束在 corruption、safety 与 mapped operation 下是否有用。最终产出不是一个“冠军模型”，而是一套最低报告清单：constraint-on/off、prior misspecification、paper/code parity、corruption stress、safety cost 和 application-stage comparison。

## 六、章节结构与每节任务

### 1. Introduction（约 1,000–1,200 词）

建议六段，不在引言里提前堆所有数字。

1. **问题场景**：风电预测从 benchmark accuracy 走向高渗透率电网决策，物理约束被用于提高可行性和可靠性。
2. **概念缺口**：`physics-informed/constrained` 是一个过宽标签；相同标签可能对应静态历史先验、解析物理、训练损失、前向结构或 post-hoc correction。
3. **评价缺口**：clean accuracy 与一次模块消融不足以识别物理约束的独立贡献、实现忠实度或失配风险。
4. **已有工作不足**：现有综述重在模型类别和平均精度；可复现性研究重在一般 ML，但尚未把 constraint lifecycle 作为风电领域审计对象。
5. **本文做什么**：一句话引出 framework → pilot audit → PCT case → exploratory stress test。
6. **贡献与边界**：四项贡献各一句，紧接一句 non-claim，明确本文不证明约束普遍有害。

### 2. Related Work（约 900–1,100 词）

只分三组，避免按模型名称流水账：

1. physics-informed / physics-constrained learning 的知识注入方式；
2. wind forecasting 的评价、benchmark 和 decision value；
3. ML reproducibility、reporting checklist 与 software audit。

本节最后用一张 gap table 收束：已有综述是否区分 provenance、stage、inference dependency、paper/code parity、constraint-specific harm。表中最后一行为本文。

### 3. Constraint Lifecycle Audit Framework（约 1,200 词）

这是 framework，不出现语料比例。

- 3.1 Unit of analysis：每一篇论文中的每一种 physical constraint，而不只是 paper-level 标签；若一篇包含多种约束，说明 primary-constraint 或 multi-label 规则。
- 3.2 D1–D5 operational definitions：每个取值配一个正例、反例和边界案例。
- 3.3 Coding decision tree：D1 与 D3 分离，D2 按梯度/前向图/post-hoc 判定。
- 3.4 Audit outputs：study-level record、constraint-level record、code-search record、harm/ablation record。

### 4. Pilot Field Audit Protocol（约 1,200–1,500 词）

- 4.1 databases、search engines、检索日期与逐库 query；
- 4.2 eligibility criteria 与“显式物理约束”的判定规则；
- 4.3 53→48→46 的唯一 ledger 与去重键；
- 4.4 full-text coding、编码者身份、盲法、仲裁流程；
- 4.5 reliability：对真实双人覆盖部分报告 κ/α 和直接一致率；未覆盖全量时必须说明；
- 4.6 code search protocol：作者主页、GitHub、paper repository、data-availability、检索日期；
- 4.7 analysis：只做描述性统计，不做总体推断或“发表偏倚”检验。

### 5. Field Audit Results（约 1,000–1,300 词）

结果顺序固定为：

1. corpus composition；
2. D1–D3 lifecycle map；
3. D4 code-search status；
4. D5 negative-effect/harm reporting；
5. broad ablation 与 strict physical isolation 的差异。

结果段只写观察，不提前批评作者动机。例如：

> Of the 46 included studies, 24 contained an intervention that directly switched or reweighted the physical constraint, whereas 22 ablated a broader architectural module. The latter designs do not isolate the contribution of the physical constraint from that of the surrounding representation capacity.

不要写：

> Nearly half of the papers use fake ablations to exaggerate the benefits of physics.

### 6. Static Software Case Study: PCT（约 800–1,000 词）

- 6.1 为什么选 PCT：唯一识别到的公开代码案例，而不是因为它“最差”；
- 6.2 paper specification：标准 JS 的公式；
- 6.3 code path：固定 commit、文件、函数和调用链；
- 6.4 mathematical verification：`F.kl_div(log p,q)=KL(q||p)` 及 reverse-JS-type 组合；
- 6.5 negative control：证明 paired product-kernel KDE 与标准二维 KDE 等价，明确记录被撤回的错误指控；
- 6.6 boundary：不推断下游 RMSE 后果，不外推到 TgDPF 或其他无代码方法。

### 7. Exploratory Downstream Stress Tests（约 900–1,100 词）

建议主文只保留两个最能连接 lifecycle 的问题：

1. **clean vs corrupted telemetry**：证明标准测试排名不能代表 stress behavior；
2. **application-stage comparison**：no guardrail / post-hoc clipping / jointly trained guardrail，展示安全约束的收益—代价关系。

mapped dispatch、跨域结果、全模型大表、fairness control 放补充材料。若三臂不是相同 backbone 与相同训练预算，则标题使用 `illustrative comparison`，不要使用 `causal ablation`。

### 8. Discussion（约 1,300–1,600 词）

建议五段：

1. 回答四个 RQ，不复述全部数字；
2. 解释 taxonomy 的方法学价值：把可获得性、实现与验证问题从“physics”标签中拆开；
3. 解释 field audit 的含义：现有证据不足以区分 constraint benefit 与 module benefit；
4. 解释 PCT 与 stress test 的边界：一个案例证明审计必要，不证明普遍错误；
5. 给作者、审稿人和期刊的 reporting checklist。

### 9. Limitations（单列，约 500–700 词）

必须主动写：pilot corpus、检索渠道限制、全量双人编码状态、`not-found` 不等于不存在、单一代码案例、替代数据与 exploratory stress test、mapped dispatch 的操作点依赖。

### 10. Conclusion（约 200–250 词）

结论只做三件事：重申审计对象、总结最稳观察、提出最低报告标准。不要重新宣布“physics constraints are defensive guardrails”这一一般结论。

## 九、最值得参考的论文及应学习的写法

### 1. Kapoor & Narayanan (2023), *Leakage and the reproducibility crisis in machine-learning-based science*

链接：[Patterns, DOI 10.1016/j.patter.2023.100804](https://doi.org/10.1016/j.patter.2023.100804)

这是与本稿结构最接近的范文：**问题定义 → 跨领域调查 → taxonomy → 单领域复现案例 → reporting solution**。最应学习的是其边界意识：当检索无法构成严格系统综述时，作者明确把结果称为 lower bound，而不是假装总体无偏。本稿可以借用这种“主动降级反而增强可信度”的写法。

### 2. D'Amour et al. (2022), *Underspecification Presents Challenges for Credibility in Modern Machine Learning*

链接：[JMLR 23(226), 1–61](https://www.jmlr.org/papers/v23/20-1335.html)

学习其**先命名概念，再给简单例子，最后跨场景 stress test**的长文结构。尤其值得模仿的是：stress test 不是为了再争一次 IID leaderboard，而是检测标准验证指标没有约束住的行为。本稿第7节应按这个逻辑写，而不是重新写 Ultra-LSNT 排名。

### 3. Gundersen & Kjensmo (2018), *State of the Art: Reproducibility in Artificial Intelligence*

链接：[AAAI, DOI 10.1609/aaai.v32i1.11503](https://doi.org/10.1609/aaai.v32i1.11503)

学习其**先定义可复现性层级和可编码变量，再调查论文**的顺序。该文把 Method、Data、Experiment 分成指标后再统计400篇论文，说明 taxonomy 必须先于比例。它也提示本稿要公开变量、分母、抽样/筛选过程与不确定性。

### 4. Tricco et al. (2018), PRISMA-ScR

链接：[PRISMA-ScR 官方页面](https://www.prisma-statement.org/scoping)

这是方法报告底线，而不是一般引用。PRISMA-ScR包含20个必需报告项和2个可选项。本稿至少要交代：为什么用 scoping review、protocol、eligibility、全部信息源、完整 search、筛选、charting/coding、critical appraisal 是否执行、结果综合方式和局限。

### 5. Levac, Colquhoun & O'Brien (2010), *Scoping studies: advancing the methodology*

链接：[Implementation Science, DOI 10.1186/1748-5908-5-69](https://doi.org/10.1186/1748-5908-5-69)

学习其“研究问题—检索—选择—charting—collating”的方法链。对本稿最重要的是：scoping audit 的目标是 map concepts, evidence types and gaps，而不是在异质语料上硬做总体效果推断。

### 6. Krishnapriyan et al. (2021), *Characterizing possible failure modes in physics-informed neural networks*

链接：[NeurIPS 2021](https://proceedings.neurips.cc/paper/2021/hash/df438e5206f31600e6ae4af72f2725f1-Abstract.html)

学习其谨慎的 failure-mode 写法：标题和摘要使用 `possible failure modes`，并通过对照排除“只是网络表达能力不足”这一替代解释。本稿不能只展示异常，还应写出 negative control：PCT 的 KDE 指控被证明不成立，而 reverse-JS 方向差异保留。

### 7. Pineau et al. (2021), *Improving Reproducibility in Machine Learning Research*

链接：[JMLR 22(164)](https://jmlr.org/papers/v22/20-303.html)

学习其**问题诊断后给制度化 checklist**的收口方法。本稿的最终价值不应停在“发现别人报告不足”，而应提供作者、审稿人和编辑可执行的 Constraint Lifecycle Reporting Checklist。

### 8. Optis et al. / WE-Validate (2022), *Evaluating wind speed and power forecasts ... using an open-source and systematic validation framework*

链接：[Renewable Energy, DOI 10.1016/j.renene.2022.09.111](https://doi.org/10.1016/j.renene.2022.09.111)

学习其风电领域的**框架—开源工具—benchmark exercise**组合，以及对 robust、resistant、equitable metrics 的强调。它可以帮助第7节从一般 ML stress test 落回风电评价语境。

### 9. Madsen et al. (2005), *Standardizing the Performance Evaluation of Short-Term Wind Power Prediction Models*

链接：[DOI 10.1260/030952405776234599](https://doi.org/10.1260/030952405776234599)

学习其“先规定公平评价协议，再比较预测系统”的写法。该思路可用于约束本稿的 downstream 结果：不同模型或 application stage 如果数据、horizon、scaler、预算不一致，就不能写 causal superiority。

### 10. Lipton & Steinhardt (2019), *Troubling Trends in Machine Learning Scholarship*

链接：[ACM Queue, DOI 10.1145/3317287.3328534](https://doi.org/10.1145/3317287.3328534)

把它作为语言自检标准：区分观察、解释和推测；不要把调参收益写成机制收益；不要用数学符号制造“已证明”的印象；不要把 `not-found`、`unreported`、`mismatch` 混成 `irreproducible`。

## 十、可直接执行的写作技巧

### 宏观结构

1. **先定义名词，再统计名词**：taxonomy 章节不出现比例，结果章节不重新发明类别。
2. **每个贡献只承担一种证据责任**：C1定义、C2描述、C3核查、C4说明现实关联。
3. **强案例不承担普遍性**：PCT 越具体越可信；不要为了显得重要而外推到整个方法族。
4. **压力测试回答“标准评估漏掉什么”**：不再回答“谁排名第一”。
5. **把撤回写成 negative control**：KDE 指控被推翻不是丢分项，而是审计协议能纠错的证据。

### 段落级写法

每段使用 `claim → evidence → boundary → implication` 四步：

> **Claim:** Strict constraint isolation was not universal in the included corpus.  
> **Evidence:** Twenty-four studies directly switched or reweighted the physical constraint, whereas twenty-two removed only a broader architectural module.  
> **Boundary:** This coding does not establish that the reported gains are invalid; it shows that the constraint-specific contribution cannot be identified from those module-level comparisons.  
> **Implication:** Future evaluations should include a constraint-on/off comparison under a fixed architecture and training budget.

### 结果措辞等级

| 证据 | 推荐动词 | 禁用动词 |
|---|---|---|
| 描述性语料统计 | observed, identified, documented, was not reported | proved, demonstrated bias, universally lacks |
| 静态数学核查 | implements, differs from, is equivalent to | causes degradation, invalidates the paper |
| exploratory stress test | illustrates, suggests under the tested protocol | establishes, guarantees, generalizes |
| 未显著或小样本 | directionally consistent, uncertain, compatible with | non-inferior, robustly better |

### 摘要六句法

1. 领域背景与常见评价方式；
2. 未解决的审计问题；
3. 五维框架；
4. pilot corpus 与最稳描述性结果；
5. PCT 静态案例 + exploratory stress-test 的有限发现；
6. 贡献和边界：提供 protocol/checklist，不证明约束普遍有害。

摘要中最多保留三组数字：46篇、24/46 strict isolation、45 not-found + 1 mismatch。stress-test 只保留一个最能说明 trade-off 的结果，其他数字进正文。

## 十一、建议的写作顺序

不要从摘要或引言开写。推荐顺序：

1. 冻结 Methods：schema、unit of analysis、PRISMA、coding、code search；
2. 从唯一 CSV/ledger 自动生成 Results 与图表；
3. 写 PCT case，并把成立/撤回/未验证分栏；
4. 选定主文两个 stress tests，其余移附录；
5. 写 Discussion 与 Limitations；
6. 最后写 Introduction、Abstract、Title。

## 十二、投稿前主线验收条件

- 任一摘要主张都能指向一张表、一个公式或一个可追溯 ledger；
- 46/48/53 的分母在全文只有一种解释；
- 不把单人编码、自查或规则编码写成全量双人工一致性；
- `not-found`、`unreported`、`mismatch` 三者严格分开；
- PCT 只保留 reverse-JS-type 静态差异及 KDE 等价的 negative control；
