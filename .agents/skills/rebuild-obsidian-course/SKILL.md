# Obsidian 课程重构

## 权威规则

1. 从知识库根目录开始，先读取所有适用的 `AGENTS.md`，再读取目标课程附近的 `README.md`、课程入口、阶段 MOC、模板和项目说明。仓库规则与用户要求始终高于本 Skill。
2. 若工作区是 `F:\-`，以根 `AGENTS.md` 的第 0–6、9 节为现行事实源；不要把这些规则复制进课程目录，也不要用本 Skill 覆盖其后续更新。
3. 按需读取以下参考文件：
   - 设计目录、字段和单向事实源时读 `references/course-contract.md`。
   - 判断任务层级、拆批、恢复或执行治理时读 `references/execution-protocol.md`。
   - 进行 C 级复审或准备 A/B 级正式验收时读 `references/audit-rubric.md`。
4. 可运行 `scripts/preflight_course.py` 做只读结构预检。脚本只能发现机械问题，不能替代逐卡阅读、来源核验、教学质量判断或正式验收。

## 先判定任务层级

开始写入前明确选择一个层级：

- `local_task`：修一张卡、一个公式、一个链接、一份作业或一个阶段内的小范围问题。只满足普通任务完成标准，不扩张为整门课程治理。
- `full_course`：用户明确要求新建、完整重构、系统补全或治理一门课程。执行完整课程流程，按阶段拆批并维护唯一执行清单。
- `formal_release`：用户要求正式完成、发布或宣布整门课程达标。在 `full_course` 基础上必须达到 A 或 B 级验收。

“重构整门课程”默认是 `full_course`，但不自动等于已经正式发布。范围不清时选择能完成用户目标的最小层级；只有破坏性边界或课程身份无法可靠判断时才询问。

## 工作流

### 1. 只读预检

1. 检查仓库结构、适用规则、工具入口和 `git status --short`。
2. 定位唯一课程目录、项目目录、课程学习路径、来源索引、阶段 MOC、作业总索引、质量审计和重构执行清单。
3. 清点 Markdown、代码、数据、测试、历史作业、空壳、重复候选、根目录散卡、断链和未提交修改。
4. 运行只读预检；示例：

```powershell
$skillRoot = if ($env:CODEX_HOME) { Join-Path $env:CODEX_HOME 'skills\rebuild-obsidian-course' } else { Join-Path $HOME '.codex\skills\rebuild-obsidian-course' }
python (Join-Path $skillRoot 'scripts\preflight_course.py') --vault "F:\-" --course "02-时间序列分析" --project "03-Projects\02-时间序列分析"
```

5. 先报告事实和范围，再写入。不得把脚本警告直接当作删除依据。

### 2. 冻结范围和恢复点

- `local_task`：只列当前文件、直接权威关系和受影响入口；历史欠债写入既有治理清单。
- `full_course`：维护 `03-Projects/<路径>/质量审计/课程重构执行清单.md`，一门课程为治理单位，一个阶段为默认批次。
- 大规模移动、合并、重命名或清退前，按仓库规则建立可恢复快照并先 dry-run。
- 不覆盖用户已有修改，不使用破坏性 Git 命令，不把聊天摘要当作进度源。

### 3. 审查现状并治理

逐项判断 `保留 / 补写 / 合并 / 迁移 / 清退 / 待人工确认`：

- 先检查当前目标文件、阶段入口和直接链接，再扫描历史结构问题。
- 默认只记录历史欠债；仅处理阻断当前任务的问题，或用户已明确授权的课程治理范围。
- 合并前选择 canonical 文件并保留正确的独有内容、个人批注、错题和来源。
- 清退前进入 `.recovery-hold/<YYYY-MM-DD>/`，修复引用并记录证据；低质量不等于可无记录删除。
- 知识卡正文不得脚本批量生成、模板灌水或先建空壳后统一补写。

### 4. 建立最少充分来源架构

1. 联网核验官方课程页、教学大纲、开放教材、讲义、作业、代码仓库、版本和许可证；优先第一方来源。
2. 先选择一个主 Spine。只有它存在可证明的知识、实践或作业缺口时才增加 Co-Spine 或 supplement。
3. 每个补充来源记录角色、具体缺口、使用范围和退出条件。来源数量不是质量指标。
4. 多源时先抽取学习目标、章节、先修、术语、深度和作业，再去重、统一术语、依赖排序、裁决冲突和补齐缺口；最终只呈现一条本地路径。
5. 建立“来源章节/讲次 → 本地阶段 → 知识卡 → 作业”的覆盖矩阵。多源融合自评低于 85 时先重构来源方案。
6. 仅在官方课程缺少必要实践或综合任务时引入开源项目，并核验 URL、tag/commit、许可证、环境、数据、Starter Code 和验收方式。

### 5. 设计学习路径与前置层

- 只保留“课程学习路径 → 阶段 MOC → 知识卡/作业”三级导航。
- 课程根目录只保留课程入口和必要来源索引，知识卡全部归入 `00-前置知识/` 或有序阶段目录。
- 先盘点必需前置，区分已具备、需补全、需新建和可选扩展。
- 已有低质量前置卡必须先用正规知识卡模板补全；不能把死链、占位页或一句话术语页当作前置。
- 上游正式课程过大时创建当前课程的最小桥接卡，说明需要什么、不展开什么、完整内容去哪里学，并设置最低通过标准。
- 课程路径给出目标、最低前置、来源、阶段顺序、阶段目标、知识卡、作业、验收和阶段衔接；不能只列文件名。
- 每个阶段必须说明“现在为什么学、学完能做什么、完成哪些作业后进入下一阶段”，并设置复习/回顾节点。
- 每轮阶段验收后记录学习者的错误、薄弱点、复习入口和下一轮改进，形成“学习—作业—验收—复盘”闭环。

### 6. 逐卡生产

一张卡必须完成完整闭环后才能开始下一张：

1. 读取目标卡、阶段 MOC、相邻卡、重复候选、直接前置和来源。
2. 判断保留、补写、合并、迁移、新建或清退。
3. 确认课程前缀、阶段目录、`course`、`stage_moc` 和真实 `upstream`。
4. 只对知识卡使用仓库规定的正规教学模板；作业、项目、报告和目录禁止套知识卡模板。
5. 写出问题动机、术语、正式定义、条件、推导或实现、例子、反例/误区、检索练习、通过标准、来源和课程连接。
6. 检查与相邻卡的重复、缺口和认知坡度。
7. 知识依赖只维护 `upstream`；真正起点省略该字段。下游和可完成作业使用 Dataview 反向派生。
8. 每张非豁免知识卡必须展示“学完后可以完成”派生区块，至少能查询作业、检索练习或可执行产物；不手工复制作业清单。
9. 验证内容、公式、代码、Frontmatter、链接、表格和直接权威关系，再将该卡标记为 `validated`。

不得同时把多张卡置于 `in_progress`，不得脚本批量生成定义、推导、例子、习题或总结。

### 7. 建设作业体系

- 所有作业与可执行项目进入 `03-Projects/<路径>/`；`02-Knowledge/` 不维护第二套作业源。
- 规模只使用 `lesson | stage | capstone`，分别进入 `课后作业/`、`阶段作业/`、`大作业/`；考试、实验、复现、竞赛、阅读等写入 `assignment_format`。
- 作业—知识关系只维护在作业 `requires`；确保所需知识在作业出现前已经教授。
- 审查历史“李宏毅式、4-Tier、Boss、阶梯、HWxx”等候选作业；按仓库阈值保留、补写、合并或安全清退，规范名称不得保留营销式标签。
- 课后作业验证紧密知识点的理解、基础推导、最小实现和常见错误；阶段作业验证多模块整合、实验/分析和阶段产物；大作业验证问题定义、数据处理、方法选择、实现、评价、错误分析、改进和展示，不能只是放大版课后题。
- 在许可证允许范围内翻译开放作业，保持题号、公式、数据和提交语义；本地融合任务必须如实标注，不能冒充官方作业。
- 每份作业必须包含身份、目标、边界、详细题目、环境、提交产物、Rubric、引导与自检、来源及后续入口。
- 作业正文还应区分基础要求、必要提示、常见错误和可选进阶任务；进阶任务不能成为完成主任务的隐性前置。
- 一个任务能可靠验收多个紧密知识点时不要形式化拆分；完整课程应有形成性练习、阶段综合任务和至少一个真正跨阶段的 capstone，但数量服从课程目标而非配额。

### 8. 最小验证

根据修改范围从小到大运行：

1. 当前文件的 Frontmatter、链接、表格、公式、代码语法或最小运行样例。
2. Skill 预检脚本和仓库已有的占位、Frontmatter、链接、重复、作业目录、课程路径审计脚本。
3. Starter Code、测试、数据入口与复现实验。
4. `git diff --check`、修改文件清单和关键 diff。

不得为了通过检查而降低标准、删除错误记录、改坏测试或把工具噪声说成通过。明确区分本次引入、历史欠债、工具噪声和未验证项。

### 9. 验收与迭代

- 单文件完成：检查内容、目录、Frontmatter 和直接权威关系。
- 批次完成：运行结构与目标范围验证，不强制五维总评分。
- 阶段完成：可执行 C 级只读复审，报告必须标记“非独立复审”。
- 正式课程发布：必须由独立子智能体进行 A 级全量复审，或由独立会话/模型进行 B 级复审。
- 通过门槛：总分至少 85，每维至少 16，无阻断问题；按“审计 → 修改 → 验证 → 复评”循环。
- 环境无法提供 A/B 时，明确报告正式发布未完成，不得把 C 级伪装为独立复审。

### 10. 特定领域教师模式 (Teacher Personas)

当接收到如“给我上一节某某课”的授课指令时，必须启动大纲编译器（Syllabus-to-Cards Compiler）模式，并依据课程领域加载对应适配规则：

1. **大纲编译核心原则**：严禁生成单篇包含全部讲义、推导、代码和练习的超长流水账。必须自动将教学意图拆解为独立的概念卡、推导卡、代码卡，并严格执行“逐卡生产”和“三级导航”规则。
2. **大学数学教师模式**：
   - 启用 `Obsidian数学知识点证明模板.md`，执行严格的符号证明与双重验算。
   - 分离概念定义与数学推导；练习题不得在知识卡中直接解答或无序罗列，必须下发至 `03-Projects/<课程>/课后作业/` 形成独立验收链。
3. **AI / 机器学习教师模式**：
   - 采用“直觉剖析 $\to$ 数学形式化 $\to$ 代码实现”的教学路径。
   - 自动生成配合 PyTorch 最小可运行示例（写入 `scripts/` 与 `tests/`）的 Lab 作业，并关联核心经典论文的 Claim-Evidence 精读与消融实验验收。
4. **IELTS / 语言备课模式（自适应回流闭环）**：
   - 生成下一阶段新课前，系统必须主动检索 `04-Review/` 中标记了 `weak: true` 的错题和薄弱点卡片。
   - 在 `03-Projects/` 生成下一阶段作业时，自动在开头插入针对历史薄弱点的定制化专项复习模块（如特定语法修正、听力错音辨析）。
   - 将 Band 5-9 评分标准固化为阶段作业的 Rubric 验收标准。

## 完成报告

交付时简洁报告：

1. 任务层级与实际范围。
2. 修改文件、治理动作和恢复位置。
3. 采用的 Spine/补充来源及未核验项。
4. 已运行检查、真实结果和残余历史欠债。
5. 验收等级、五维分数、是否独立、阻断项和是否达到正式发布标准。
